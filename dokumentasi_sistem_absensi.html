1. Mengapa Jalur Server Terasa Sedikit Lebih Lama & Jarak Wajah Harus Lebih Pas?

Berdasarkan pengujian nyata di smartphone dan log server, berikut adalah analisis ilmiah dan teknis mengapa terdapat perbedaan kecepatan serta sensitivitas jarak antara kedua mode:

Fakta Pengujian di Lapangan:
  • Mode On-Device (⚡): Latensi total hanya ~50 – 80 milidetik (0,05 detik). Terasa instan seperti kamera biasa karena seluruh komputasi berjalan di NPU/CPU lokal smartphone tanpa menyentuh internet.
  • Mode Cloud Server (🌐): Latensi total berkisar ~1,0 – 1,4 detik. Terdapat perjalanan transmisi paket data (Round Trip Time) bolak-balik dari ponsel melalui pemancar 4G LTE/Wi-Fi ke server VPS di internet.

A. Bedah Rincian Waktu (Latency Breakdown) Mode Server:

  1. Pengambilan & Kompresi Frame di HP (~80 ms): Kamera menangkap foto mentah (~1,7 MB), lalu dikompresi ke 1280px (~85 KB) agar efisien dikirim via jaringan seluler.
  2. Upload Jaringan 4G LTE (~400 – 600 ms): Mengirim file 85 KB dari smartphone ke IP publik VPS (103.175.206.22) melalui sinyal radio seluler.
  3. Inference AI di CPU VPS (~150 – 250 ms): Server melakukan praproses CIELAB CLAHE, inference deteksi objek YOLOv26, ekstraksi embedding MobileFaceNet TFLite, serta kalkulasi Cosine Similarity.
  4. Download Respon JSON ke HP (~200 – 300 ms): Respon daftar siswa hadir dikirimkan kembali ke smartphone untuk memperbarui UI dan mengaktifkan haptic feedback getar.

B. Mengapa Jarak Wajah Mempengaruhi Hasil di Server?

Ketika Anda berdiri pada jarak 1,5 – 2,5 meter (atau saat berkelompok 5–6 orang):

  • Kerapatan Piksel (Pixel Density): Dari jarak 2 meter, area wajah di dalam frame kamera hanya menempati sekitar 40×40 hingga 60×60 piksel. Ketika dicrop dan di-resize ke ukuran standar MobileFaceNet (112×112 piksel), detail halus seperti sudut kelopak mata dan garis hidung mengalami penurunan ketajaman (resolusi rendah).
  • Solusi Face-Level CLAHE & Lanczos: Untuk mengatasi hal ini, kita telah menambahkan algoritma Lanczos4 Interpolation dan Face-Level CLAHE pada potongan wajah 112×112 di server, sehingga kontur wajah dari jarak jauh tetap dipertegas dan dikenali dengan skor kemiripan di atas ambang batas (0,4059 > 0,3800).

4. Arsitektur & Peranan Kritis Firebase Cloud Firestore dalam Sistem Absensi

Dalam penelitian skripsi ini, Google Firebase Cloud Firestore bertindak sebagai Single Source of Truth (Pusat Data Tunggal Terpadu) yang menghubungkan aplikasi smartphone guru dengan server AI VPS. Berikut adalah peran strategis dan implementasi teknisnya:

Mengapa Menggunakan Firebase Cloud Firestore?

Firestore adalah basis data NoSQL berorientasi dokumen yang memiliki latensi sangat rendah, mendukung sinkronisasi real-time secara dua arah, dan memiliki fitur Offline Persistence otomatis. Ini menjamin aplikasi absensi tetap dapat berjalan tanpa hambatan meskipun koneksi internet di sekolah sedang tidak stabil.

B. Keamanan & Perlindungan Privasi Data Biometrik (Nilai Plus Skripsi):

Prinsip Privasi "One-Way Mathematical Representation":
Salah satu keunggulan ilmiah sistem ini adalah TIDAK menyimpan file foto wajah mentah siswa di dalam database utama. Sebagai gantinya, Firestore hanya menyimpan vektor numerik 192 dimensi hasil inferensi MobileFaceNet.
Vektor ini bersifat irreversible (tidak dapat direkonstruksi kembali menjadi foto wajah asli), sehingga memenuhi standar etika privasi biometrik internasional (GDPR / UU Perlindungan Data Pribadi). Jika database diretas, data tersebut hanyalah deretan angka desimal acak yang tidak dapat disalahgunakan.

C. Integrasi Ganda Dua Arah (Dual SDK Architecture):

Sistem ini memanfaatkan dua mekanisme integrasi Firebase secara bersamaan:

  1. Sisi Klien Smartphone (Flutter): Menggunakan pustaka resmi cloud_firestore.
    • Saat pendaftaran siswa baru: Vektor embedding diekstraksi dan langsung disimpan ke Firestore.
    • Sebelum kelas dimulai: Aplikasi mengunduh vektor siswa satu kelas dan menyimpannya ke memori lokal Hive DB untuk mendukung absensi instan secara offline.
  2. Sisi Server AI VPS (Python): Menggunakan pustaka resmi firebase-admin (Admin SDK) dengan kredensial aman firebase-adminsdk.json.
    • Saat server menerima foto dari mode 🌐 YOLOv26: Begitu wajah cocok (Cosine Sim > 0.28), server mengeksekusi penulisan status hadir ke koleksi absensi_harian secara asinkron (background task) dalam < 0.1 detik.

5. Kronologi & Rekayasa Teknis Pemecahan Masalah (Problem Solving)

Berikut adalah catatan tahapan rekayasa perangkat lunak dan AI yang telah kita selesaikan secara terperinci:

1. Mengatasi Crash "Segmentation Fault (Core Dumped)" pada VPS Ubuntu:

Akar Masalah: PyTorch secara bawaan mengimpor modul triton (JIT CUDA compiler). Pada VPS CPU-only tanpa GPU NVIDIA, pustaka ini memanggil driver CUDA yang tidak ada sehingga memicu silent segmentation fault saat pertama kali menerima request gambar.

Solusi: Menghapus paket triton (pip uninstall -y triton triton-nightly) dan menonaktifkan kompilator Torch Dynamo via environment variable: TORCH_COMPILE_DISABLE=1 dan TORCHDYNAMO_DISABLE=1.

2. Kalibrasi Ambang Batas Kemiripan (Cosine Threshold & Margin Verification):

Akar Masalah: Ambang batas bawaan model awalnya disetel pada 0.65 (khusus ArcFace 512-d di kondisi foto studio). Sedangkan MobileFaceNet 192-d pada kamera video real-time menghasilkan rentang kemiripan 0.40 – 0.52 untuk orang yang sama dan < 0.20 untuk orang yang berbeda.

Solusi: Menyesuaikan threshold ke 0.38 serta menambahkan proteksi Margin Verification (Selisih Minimal 0.06). Jika selisih skor kandidat pertama dan kedua terlalu tipis, sistem otomatis menolaknya sebagai ambigu untuk mencegah salah orang.

3. Optimasi Respons Kilat Transaksi Firestore:

Solusi: Memindahkan fungsi penulisan log kehadiran Firebase Firestore ke dalam asyncio.create_task(asyncio.to_thread(...)) di latar belakang, sehingga API HTTP server langsung merespons ponsel dalam waktu < 0.1 detik tanpa menunggu database selesai menulis.

4. Peningkatan Kualitas Citra Jarak Jauh (1280px & Face-Level CLAHE):

Solusi: Mengubah resolusi kompresi klien dari 960px menjadi 1280px (Lanczos4) serta mengaplikasikan CLAHE langsung pada potongan crop wajah 112×112 piksel di server agar identik dengan mekanisme ekstraksi di aplikasi ponsel.

5. Pembersihan Lalu Lintas Bot Internet:

Solusi: Menjalankan Uvicorn dengan parameter --no-access-log untuk menyaring kebisingan pemindaian otomatis crawler internet (seperti Shadowserver dan Shodan) sehingga terminal VPS tetap bersih dan fokus pada log absensi.

6. Rekomendasi Penggunaan untuk Sidang Skripsi

Poin Unggulan yang Dapat Dipresentasikan:
  1. Konsep Saklar Hybrid (Dual-Engine): Aplikasi memberikan fleksibilitas penuh kepada institusi sekolah:
    • Gunakan Mode On-Device jika sekolah berada di wilayah minim sinyal internet atau membutuhkan respon super instan (0,05 detik).
    • Gunakan Mode Server YOLOv26 ketika guru ingin melakukan absensi rombongan 5–6 siswa sekaligus dalam satu jepretan kamera secara terpusat.
  2. Keandalan Algoritma CLAHE: Terbukti menstabilkan kontras adaptif pada kanal Luminansi (L) di CIELAB, sehingga sistem kebal terhadap backlight jendela kelas dan bayangan ruangan.
  3. Efisiensi Arsitektur: Sistem berhasil berjalan stabil pada VPS ekonomis (4GB RAM, CPU-Only) tanpa memerlukan kartu grafis (GPU) mahal berkat optimalisasi MobileFaceNet TFLite dan pembersihan runtime Triton.
